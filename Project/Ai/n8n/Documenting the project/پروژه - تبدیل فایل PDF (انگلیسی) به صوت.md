# ۱ خلاصه پروژه

پروژه **neiten_text_audiobot** (ربات تلگرامی «PDF & Speech Bot» با آی‌دی @pdf_speech_bot) روی پلتفرم n8n Cloud پیاده‌سازی شده است و کارکرد آن به این صورت است که کاربر از طریق ربات تلگرام مینی‌اپ را باز می‌کند، فایل PDF خود (فقط متن انگلیسی) را در مینی‌اپ بارگذاری می‌کند؛ سپس ورک‌فلو متن را از PDF استخراج می‌کند، متن را با سرویس تبدیل متن به گفتار ElevenLabs به فایل صوتی تبدیل می‌کند و فایل صوتی نهایی را در تلگرام برای همان کاربر ارسال می‌کند. چون از پلن رایگان ElevenLabs استفاده می‌شود، هر ماه حدود ۴۰٬۰۰۰ کریدیت در دسترس است و برای صفحه‌ای با حدود ۷۰۰ کاراکتر، تقریباً ۱٬۵۰۰ کریدیت مصرف می‌شود؛ برای مقابله با اتمام کریدیت یا خطا، زنجیره‌ای از ۴ اکانت ElevenLabs به‌صورت Failover طراحی شده است تا اگر یک اکانت خطا داد، به‌طور خودکار اکانت بعدی امتحان شود.

# ۲ نقشه پروژه بطور خلاصه

ترتیب کامل ورک‌فلو به این صورت است:

**الف) شروع و پیام‌های تلگرام** Telegram Trigger ← If - اگر پیام /start باشد ← نود /start-Message (پیام خوش‌آمدگویی) - اگر پیام متنی باشد ← نود text-message (دعوت به کلیک روی دکمه مینی‌اپ)

**ب) سرو مینی‌اپ** Webhook_ServeMiniApp ← Respond_HTML وب‌هوک اول درخواست باز شدن مینی‌اپ را می‌گیرد و Respond_HTML کد HTML صفحه مینی‌اپ (تم تیره، ریسپانسیو) را با Content-Type: text/html; charset=utf-8 به مرورگر تلگرام تحویل می‌دهد.

**ج) دریافت و پردازش فایل** Webhook_ReceiveMiniApp ← Check File Format1 - فایل نامعتبر ← نود File upload message - فایل معتبر (PDF) ← نود Extract From File1 یعنی وقتی که فایل PDF آپلود کردین، و بر روی دکمه آپلود کلیک کردین، و فرایند ارسال فایل به n8n آغاز میشه.

**د) زنجیره تبدیل متن به صوت با** **Failover چهار سطحی** Call_ElevenLabs_API_1 ← Check_Audio_Generated_1 ← Call_ElevenLabs_API_2 ← Check_Audio_Generated_2 ← Call_ElevenLabs_API_3 ← Check_Audio_Generated_3 ← Call_ElevenLabs_API_4 ← Check_Audio_Generated_4 - مسیر موفق ← Success and Send an audio file1 (ارسال صوت به کاربر) - مسیر ناموفق ← Error- convert text to speech

نکته: در ورک‌فلو، نود Decompress DOCX1 و نمونه Sample English story هم دیده می‌شوند، اما این نود غیرفعال است و جزو مسیر فعال محسوب نمی‌شود.

# ۳ تعریف نحوه کار هر نود

**نود** **Telegram Trigger:** شروع‌کننده پروژه است؛ هر پیامی که به ربات تلگرام برسد این نود فعال می‌شود و داده پیام را به نود بعدی پاس می‌دهد.

**نود** **If:** خروجی تریگر را بررسی می‌کند و جریان را مسیریابی می‌کند: اگر پیام دقیقاً /start باشد به مسیر خوش‌آمدگویی می‌رود و اگر پیام متنی دیگر باشد به مسیر پیام راهنما.

**نود /****start-Message:** وقتی کاربر /start می‌زند، پیام خوش‌آمدگویی برای او در تلگرام ارسال می‌شود.

**نود** **text-message:** وقتی کاربر پیام متنی بفرستد، پیامی حاوی دعوت به "کلیک روی دکمه مینی‌اپ" ارسال می‌کند تا کاربر وارد  مینی اپ«PDF & Speech Bot» شود.

**نود** **Webhook_ServeMiniApp:** وب‌هوکی که درخواست باز شدن مینی‌اپ (یعنی وقتی کلیک روی همان دکمه مینی اپ در بات کنید) را می‌گیرد و روی حالت «Using Respond to Webhook Node» تنظیم شده است.

**نود** **Respond_HTML:** کد کامل HTML/CSS/JS صفحه مینی‌اپ را با هدر Content-Type: text/html; charset=utf-8 به مرورگر تلگرام برمی‌گرداند و صفحه در مینی‌اپ نمایش داده می‌شود. داخل این کد، درخواست fetch باید دقیقاً برابر Production URL نود Webhook_ReceiveMiniApp باشد؛ آدرس فعلی: https://neiten.artrecordbeats.xyz/webhook/process-miniapp. کد مینی‌اپ پس از ساده‌سازی، فقط شامل محل آپلود فایل PDF است؛ انتخاب‌گر صداپیشه (voiceSelect) به‌طور کامل حذف شده و voice_id دیگر از مینی‌اپ ارسال نمی‌شود. chat_id کاربر داخل مینی‌اپ با Telegram WebApp SDK (window.Telegram.WebApp.initDataUnsafe?.user?.id) گرفته شده و همراه FormData به وب‌هوک process-miniapp فرستاده می‌شود.

**نود** **Webhook_ReceiveMiniApp:** فایل PDF آپلودشده و chat_id را از مینی‌اپ دریافت می‌کند و به نود بررسی فرمت می‌دهد.

**نود** **Check File Format1:** که در اصل یک if است، فرمت فایل را اعتبارسنجی می‌کند؛ اگر فایل معتبر نباشد به نود File upload message می‌رود (پیام خطای فرمت) و اگر PDF باشد به Extract From File1 پاس می‌دهد.

**نود** **Extract From File1:** متن را از فایل PDF  استخراج می‌کند (فایل را به داده باینری/متنی تبدیل می‌کند) و خروجی متنی را تحویل مدل زبانی ElevenLabs می‌دهد.

**نودهای** **Call_ElevenLabs_API_1 تا** **Call_ElevenLabs_API_4:** چهار اکانت/API ElevenLabs هستند که متن را به صوت تبدیل می‌کنند. نود اول (Call_ElevenLabs_API_1) درخواست TTS را می‌فرستد؛ اگر خطایی مثل اتمام کریدیت رخ دهد، نود بررسی بعدی مسیر را به نود HTTP دوم (اکانت دوم) منتقل می‌کند و همین منطق تا اکانت چهارم ادامه دارد. **نکته مهم:** چون انتخاب‌گر صداپیشه حذف شده، URL هر چهار نود باید Voice ID ثابت داشته باشد (مثلاً EXAVITQu4vr4xnSDxMaL برای Bella یا 21m00Tcm4TlvDq8ikWAM برای Rachel):

https://api.elevenlabs.io/v1/text-to-speech/EXAVITQu4vr4xnSDxMaL

یعنی عبارت وابسته به وب‌هوک {{ $('Webhook_ReceiveMiniApp').item.json.body.voice_id }} باید از URL حذف شود.

**نودهای** **Check_Audio_Generated_1 تا** **Check_Audio_Generated_4:** بعد از هر نود API، موفق بودن تولید صوت را بررسی می‌کنند؛ خروجی موفق به مسیر ارسال صوت می‌رود و خطا به اکانت بعدی.

**نود** **Success and Send an audio file1:** در صورت موفقیت، فایل صوتی تولیدشده را در تلگرام برای همان کاربر (بر اساس chat_id دریافتی از Webhook_ReceiveMiniApp) ارسال می‌کند.

**نود** **Error- convert text to speech:** اگر هر چهار اکانت خطا بدهند، پیام خطا به کاربر ارسال می‌شود.

**نود** **File upload message:** برای فایل با فرمت نامعتبر، پیام خطای آپلود برای کاربر می‌فرستد.

# ۴ خطاها و چالش‌ها

**در نودهای** **Call_ElevenLabs_API (پس از حذف صداپیشه) به علت حذف** **voiceSelect از** **HTML مینی‌اپ چالش داشتیم:** مقدار voice_id دیگر از مینی‌اپ به Webhook_ReceiveMiniApp ارسال نمی‌شد و URL نودهای ElevenLabs که به {{ $('Webhook_ReceiveMiniApp').item.json.body.voice_id }} وابسته بود ناقص می‌شد و خطا می‌داد. برای همین در هر چهار نود، یک Voice ID ثابت (مانند EXAVITQu4vr4xnSDxMaL) مستقیماً داخل URL قرار دادیم؛ در نتیجه انتظار نداریم voice_id در ورودی وب‌هوک وجود داشته باشد.

**در نود** **Respond_HTML به علت ناهماهنگی آدرس** **fetch چالش داشتیم:** اگر fetch داخل HTML با Production URL واقعی نود Webhook_ReceiveMiniApp یکی نباشد ارتباط با سرور برقرار نمی‌شود. راه‌حل: آدرس fetch باید دقیقاً برابر آدرس Production فعلی (https://neiten.artrecordbeats.xyz/webhook/process-miniapp) باشد و هنگام تغییر اکانت/دامنه n8n باید همزمان دو مورد به‌روز شود: Web App URL در @BotFather و آدرس fetch داخل HTML.

**در نودهای پیام تلگرام به علت قرارگیری در مسیر مستقیم داده باینری چالش داشتیم:** نودهای پیام‌رسان فایل باینری صوت را Overwrite می‌کردند و فایل از بین می‌رفت. راه‌حل: نودهای تلگرام به‌صورت موازی یا در انتهای مسیر قرار گرفتند تا باینری صوت قبل از ارسال از بین نرود.

**در نودهای** **HTTP Request با** **URL داینامیک به علت حالت فیلد چالش داشتیم:** وقتی URL شامل Expression است، فیلد باید صریحاً روی حالت Expression تنظیم شود وگرنه خطای HTTP 400 رخ می‌دهد؛ اگر URL ثابت است، نباید رد Expression قدیمی باقی بماند.

**در نودهای پیام تلگرام به علت دریافت** **chat_id چالش داشتیم:** چون آپلود از Telegram Mini App انجام می‌شود، chat_id در بدوه پیام تلگرام موجود نیست. راه‌حل: گرفتن آن از Telegram WebApp SDK داخل مینی‌اپ (window.Telegram.WebApp.initDataUnsafe?.user?.id) و ارسال آن با FormData به وب‌هوک؛ سپس در n8n از {{ $('Webhook_ReceiveMiniApp').item.json.body.chat_id }} استفاده می‌شود. برای امنیت، initDataUnsafe سمت کلاینت قابل جعل است؛ در نسخه عملیاتی باید initData خام هم ارسال و سمت سرور با Bot Token اعتبارسنجی شود.
